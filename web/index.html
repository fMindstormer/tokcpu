A stock Hugging Face tokenizer, used as a computer

Tokenizer CPU

This tokenizer runs Brainfuck. It is a plain tokenizer.json: no custom code, no model. One call to encode and one to decode carry out one step of a program; a loop around them repeats it:

tok = AutoTokenizer.from_pretrained("tokenizers/brainfuck") while (nxt := tok.decode(tok.encode(tape))) != tape: tape = nxt

The orange lines are all the tokenizer does: one encode and one decode, which apply exactly one rule. It keeps nothing between calls. The whole state of the computation is the string.

Everything else is ordinary code, the same for every machine: feed the output back in, and stop when it stops changing. The tokenizer never loops by itself. Without this loop, every machine on this page takes one step.

The same loop runs bigger machines. The universal one below reads a Brainfuck program from its tape; Hello World takes 154,137 steps.

What building it found

The same tokenizer file gives a browser and Python different ids

A program that runs for 150,000 ticks goes wrong if a single id is wrong, and the machine's own rules say what every tick must give, without asking any tokenizer library. So the machines became a test of the runtimes that read tokenizer.json: the Rust library behind Python's transformers, and the JavaScript ports that run models in web pages. The same checks then ran on the most-downloaded models on the Hugging Face Hub. This is the difference that reaches the most of them.

"Street" in capitals, as on a sign, through the tokenizer of bert-base-multilingual-uncased (mBERT), which lowercases text before splitting it.

JavaScript's toLowerCase follows Unicode: a capital Σ that ends a word becomes ς. The Rust library lowercases one character at a time, so it becomes σ, which Greek never writes at the end of a word. The browser's ids are exactly those of the word typed in lowercase; Python's are not. Python's own "ΟΔΟΣ".lower() gives ς, and so does the tokenizer Google released BERT with, run on Python 3.

And in llama.cpp

llama.cpp skips a step Qwen's tokenizer asks for, and answers change

llama.cpp, and Ollama and LM Studio built on it, never read tokenizer.json: the GGUF file carries the vocabulary, and llama.cpp's own code does the rest. The same checks, run on the most-downloaded GGUF repos, found that llama.cpp skips the NFC normalization Qwen 2 and 3 ask for. NFC is usually explained with accents, but it also rewrites ordinary letters in Bengali, Punjabi, Odia and Hindi.

One tick

The tape is a string. Exactly one character on it is the head: a marker that stands for a machine state and reads the character beside it. The tokenizer has one merge rule for every pair the head can form with a cell, and no other merges.

1 · encode

Find the head

BPE can only merge the head with the cell it reads, so the tape splits into single characters plus one two-character token.

2 · the id

Look up the rule

Each such pair has its own id. That id is the rule: which symbol to write, which way to move, which state comes next.

3 · decode

Print the result

The same id is also an added token whose text is the rule's output. Decoding prints it where the pair was. Every other character decodes to itself.

4 · repeat

Stop when nothing changes

A halting state has no merge rules, so its tape decodes to itself. The loop stops when the tape stops changing.

The catch: every step would have to be reversible

A token id decodes to exactly one string, and the library keeps one string per id when it saves a tokenizer. So if two rules wrote the same output, they would need two added tokens with the same text, which a tokenizer cannot hold. Taken plainly, the trick only runs machines whose every step can be undone: reversible computers.

Ordinary programs throw information away all the time. So each output carries a short tag of private-use characters that makes it unique, and the decoder has one generic rule: delete those characters. That deletion is the only place the machine forgets anything. It is a single find-and-replace with an empty replacement, the same for every machine.

One pass is not enough; the loop is the point

A single encode is a weak computer. Cognetta and Okazaki showed that BPE tokenization is a finite-state transduction: one pass can only look a bounded distance ahead. One tick here rewrites just the two characters around the head.

Repeating the tick is what makes it unbounded. With a tape that can grow, which the rules allow at either edge, repeated tokenizing can run any program a Turing machine can. The loop is three lines of Python, the same way the famous "CSS is Turing complete" demos need someone clicking.

The ladder

Rung 1, small machines. A binary counter (7 rules) and the 4-state busy beaver (24 rules), which halts after exactly 107 ticks with 13 ones on the tape, its known record.

Rung 2, one program per tokenizer. A compiler turns a Brainfuck program into a machine whose states are the program. Each instruction is one tick, and printing walks the byte to the output at the left of the tape, one nibble at a time. Hello World becomes 38,265 rules and prints in 1,194 ticks.

Your own machine. The last tab compiles a Turing machine you type into a new tokenizer, right in this page, and runs it. The compiler is a JavaScript port of the Python one and writes the same file, byte for byte.

Rung 3, one tokenizer for every program. A universal interpreter of 17,210 rules. The program is written on the tape. The head carries each instruction from ▼, the instruction pointer, to ▲, the data pointer, executes it there and walks back. Data cells are Braille characters, whose dots spell the byte. Loops can nest 64 deep. Input waits at the right end of the tape after ¦, and , takes its first character.

Parallel ticks

One encode reads the whole tape, but a single head uses two characters of it. Heads that never meet each get their rule applied in the same tick: two busy beavers on one tape finish together in 107 ticks.

Going further, a stock Split pre-tokenizer can cut the tape into two-character blocks before BPE runs. With a merge for every block, one tick rewrites the whole tape: a block cellular automaton. A phase mark after the left edge shifts the blocks by one character every other tick, so information crosses block boundaries. One demo sorts letters, odd-even transposition sort, one round per tick: ⊢◦thequickbrownfoxjumpsoverthelazydog⊣ is sorted after 30 ticks, with 704 rules.

The other runs Rule 110, which is Turing complete, in 29 rules. Every cell updates in every generation, which takes two ticks: in the first, each cell learns the value of the other cell in its block; in the second, the blocks have shifted, each cell learns its other neighbour and updates. The edges grow the tape by a cell on each side every generation. Rule 110 computes on a background that repeats forever, its ether, and the edges can grow that too: it takes 146 rules.
